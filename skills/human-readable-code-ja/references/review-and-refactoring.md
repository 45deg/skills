# レビューとリファクタリングの確認例

変更内容に当てはまる項目だけを読む。実際の契約を確認するための観点であり、プロジェクトに新しい要件を加えるものではない。

## 一つの変更で複数箇所の修正が必要になる

依頼や実際の保守履歴に基づく変更を一つ選ぶ。一緒に直す必要がある実装、呼び出し元、共有状態、設定や登録、テストを追う。保守担当者が暗黙のチェックリストを覚えていなくても、コードと契約からその関係をたどれるか確認する。

同じ方針を扱うのに連動が見えない箇所と、別々の理由で変わる処理が内部状態や広すぎるインターフェースで結び付いている箇所を区別する。保守の負担を実際に減らせるなら、必要な関係を明示するか、独立した責務を分ける。構文の類似、フォルダーの近さ、変更するファイル数だけで境界を決めない。外部との契約や生成物の都合で、複数箇所の同時更新が必要な場合もある。

## 複数の症状に共通原因がないか調べる

症状を個別に直す前に、判断の重複、特定の呼び出し元だけが使うフラグ、暗黙の呼び出し順、タイミングの回避策が、同じ契約の不足や責任の曖昧さから生じていないかを調べる。まとめて直す案を出す前に、実際の実行経路と要件から因果関係を確認する。

特例が、必要な業務ルールや外部制約を表している場合もある。その区別を保ち、分岐や回避策の数自体を品質の尺度にしない。確認した原因に対処できる、依頼の範囲内の最小限の変更を選ぶ。別々に変わる方針を一つの抽象化へ押し込んだり、対象を絞った修正をコードベース全体の再設計へ広げたりしない。

## 構造の変更案を証拠と判断の記録につなげる

関係するimportや呼び出し関係から依存先を探し、静的なグラフに現れない状態の参照、登録、実行経路も確認する。必要に応じてGit履歴を調べ、繰り返し同時に変更される箇所と、その理由を確かめる。同じコミットで変わったことだけでは責務が同じとはいえず、同時変更の履歴がないことだけでは独立しているともいえない。

対象のファイルやシンボル、必要な関係や共通原因の仮説、根拠と未確認の点、変更後の責務の境界、保つ動作と確認方法を短く記録する。小さな作業なら回答内の説明でよい。大きな変更ではプロジェクトで使っている設計メモなどを利用し、新しい文書形式を一律に要求しない。レビューでは根拠のある提案を示し、修正が依頼されている場合に実装する。

修正後は同じ変更場面をもう一度たどる。必要な依存関係が見えるようになったか、不要な結び付きが解消されたかを確かめ、別のヘルパーの裏へ移しただけになっていないか確認する。影響する境界で、保つべき動作も検証する。

## 整理によって処理の実行時点が変わる

ガード条件の内側にあった呼び出しを、無条件に評価する代入へ移すと、従来は通らなかった経路でも実行、失敗、リソース消費が起こり得る。条件式や既定値の書き方を変えるときは、真偽の結果だけでなく評価の挙動も確認する。

時計や可変オブジェクトを繰り返し読む処理を一度の読み取りにまとめると、参照する時点の状態が変わり得る。意図して同じ時点の値を使う箇所はその性質を保ち、異なる時点の値が契約に関わる箇所では読み取りを分ける。対応するフィールドや引数の並びを揃える場合も、依存関係と評価順序を保つ。

## 未使用に見える操作を削除・置換する

文字列検索だけでは、設定、登録処理、リフレクション、外部の利用者からの参照を見落とす場合がある。公開識別子、シリアライズするフィールド、コマンドラインオプションを削除・改名する前に、実際の使われ方を確認する。互換性を保つ層は、実在する利用者のために必要な場合だけ追加する。

独自実装を標準機能、DB操作、既存の依存ライブラリに置き換える前に、データ型、順序、重複の扱い、エンコーディング、失敗時の挙動を比べる。コードが減っても、契約が意図せず変われば改善とはいえない。

## 関数の抽出で参照先だけが増える

元の呼び出し元と、抽出後の呼び出し元・ヘルパーを比べる。細部を隠して主な処理を追いやすくする場合や、役立つ契約を設ける場合には、呼び出し元が一つでも抽出する意味がある。処理を転送するだけの関数の連鎖や、呼び出し元の状態を直接参照するヘルパーでは、覚えるべき前提が減らず、定義を探す手間だけが増える場合がある。

ヘルパーは、その処理が属する概念の近くに置く。再利用するからといって共通ユーティリティへ移す必要はない。ファイルやクラスを分けても、互いの内部状態を読み書きし続けるなら責務は分離できていない。

## テスト用ヘルパーが検証内容を隠す

ヘルパーがデータを準備するのか、対象処理を呼ぶのか、アサーションを実行するのかを分かるようにする。検証する動作を決める準備と期待値は、テストを読めば見える形に保つ。独自のテスト記法を作る前に、既存のパラメーター化機能や小さなデータ構築用ヘルパーを使う。

テストデータを簡単にしても、起こり得る不具合を区別する入力の違いは残す。失敗時には、実行したケース、入力、期待した結果と実際の結果が分かるようにする。認可、永続化、ネットワークの境界を迂回するモックでは、その境界の動作を検証できない。

小さな単位のテストに大規模なグローバル初期化が必要なら、依存関係の切り方を見直す。必要に応じて時刻、乱数、副作用を制御できるようにするが、テスト専用の公開メソッドや可変の切り替えフラグは増やさない。一つの動作上の主張を複数のアサーションで確かめてもよい。独立した主張ならケースを分ける。

## 最適化でコストや保証の条件が変わる

読みやすい基準実装と、実際の負荷・リソース制約に照らして比べる。計測で確認した改善と、分析上の見込みを区別する。継続して動く処理では、小さな入力を一度実行するだけでなく、入力の到着頻度や稼働時間に伴う増加も調べる。

集約、間引き、丸めで情報を捨てるなら、その損失が契約上許されるかを確認する。実際の制約を満たすためにコードが増える場合でも、保持する状態と、新しい処理同士の相互作用を考慮する。読みやすさの整理として、キャッシュ、再試行の仕組み、将来用の拡張ポイントを追加しない。

## 並列化で完了と後始末の条件が変わる

逐次処理を `Promise.all` に置き換えると、結果の並び順が入力順のままでも実行タイミングが変わる。共有状態への書き込み、レート制限、順序の前提、一部が失敗した後も動き続ける処理を確認する。成功、失敗、キャンセル、後始末をどの処理が引き受けるかを明確にする。

既存の再試行方針については、再試行する失敗の種類、上限、期限、キャンセル、再実行時の副作用を追えるようにする。キャンセル経路でも、必要なリソース解放、トランザクションの処理、報告を保つ。
