# 設計とコメントの例

作業内容に該当する例だけを参照する。以下は設計とコメントの判断を説明するための模式例であり、そのまま実行するコードや特定プロジェクトの仕様ではない。実際のコメントでは、関数名、パス、条件、保証内容を実装に合わせる。

## 実装ファイルの要約マップ

渡されたCSV文字列を検証済みレコードへ変換するファイルなら、冒頭に次の対応を置く。

```text
// CSV文字列を取り込み用の検証済みレコードへ変換する。保存は行わない。
// 処理の流れ: parseImport -> parseRows -> validateRows -> レコードまたは入力エラー
// parseRows: CSVの構文を読む。validateRows: 必須項目と型を検証する。
```

主要な処理を追う場所を示し、個々の検証規則は検証関数の近くに置く。単一の変換しかないファイルは、短い役割と入出力の対応で足りる。

## 再エクスポート中心のindex.ts

```text
// 取り込み機能の公開窓口。公開名と実装先の対応:
// parseImport: ./parse-import — CSV文字列の解析と検証
// saveImport: ./save-import — 検証済みレコードの保存
// ここでは再エクスポートする。各操作の呼び出しは利用側が行う。
```

再エクスポートの一覧を `parseImport -> saveImport` のように矢印でつなぐと、その順序で自動的に実行されるかのような誤解を招く。モジュール読み込み時の副作用がないと明記する場合は、再エクスポート先のファイルも確認する。一方、アプリケーションの起動を担う `index.*` では、実際の初期化手順と委譲先を示す。

```text
// HTTPサーバーを起動する。
// 起動順: loadConfig -> createApp(config) -> listen(app)
// 設定: ./config、ルート登録: ./app、通信待受: ./server
```

いずれも、必須のヘッダーやディレクティブの位置・意味を保って配置する。

## データで有効な状態を表す

`done`、`failed`、`result`、`error` を独立に持つと、有効な組み合わせを毎回覚える必要がある。

```text
JobState = Pending | Succeeded(value) | Failed(error)
```

直和型、タグ付きの値、生成時の検証など、言語に合う方式を選ぶ。直列化の境界でも不変条件を保つ。単純な成功・失敗には既存の結果型で十分な場合もある。

## 方針が見える中間値

仕様で値引き後に税を計算すると決まっている例:

```text
subtotal = sum(line_total(item) for item in items)
discount = calculate_discount(subtotal, policy)
taxable_amount = subtotal - discount
tax = calculate_tax(taxable_amount, tax_rule)
total = taxable_amount + tax
```

`temp1` では表せない段階を名前で示している。通貨と丸めは実際の契約で定義する。この例自体が税計算の方針を決めるものではない。段階を分けても意味が増えない単純な式はそのままでよい。

## 処理段階を図で示す

要求ごとに非公開の在庫コピーを使う予約計画の例:

```text
// 要求全体を満たせるか確認してから、計画内の在庫を減らす。
// 処理の流れ:
// 注文明細 -> SKUごとの数量を合算 -> 不足を収集
//   不足あり: 要求を拒否し、計画内の在庫は変えない。
//   不足なし: 合計数量を在庫から引き、要求を受け入れる。
// 外部在庫は更新しない。例外時は途中の計画を返さない。
```

外部サービスをまたぐトランザクションを表す図ではない。全件を先に検証しても、後続の外部書き込みが原子的になるわけではない。書き込み途中の失敗には別途、要件に合う処理が必要になる。

集約の目的と、後続へ渡す前提は次のように説明できる。

```text
// 同じSKUの数量を合算し、在庫確認で注文全体の必要数と比較する。
// 最初に出現した順序を保ち、不足一覧も注文の並び順で返す。
```

必要な段階の境界なら、成立した事実も示す。

```text
// ここでは各SKUが一度だけ現れ、その注文数量が合算されている。
// 在庫確認は、この合計数量と在庫数を比較すればよい。
```

同じ不変条件を全行で繰り返さず、次の処理を理解する場所へ置く。

## 契約と根拠を区別する

確認済みの外部サービス仕様で、同じキーを使った再送だけが同じ要求として扱われる場合:

```text
// 再送を同じ要求として扱わせるため、初回と同じキーを使う。
send(request, idempotency_key = original_key)
```

実在する仕様リンクがあれば添える。他のサービスにも同じ動作を仮定しない。経緯が未確認なら、過去の障害や作者の意図を作って理由にしない。

公開契約では、利用に必要な範囲と失敗を示す。

```text
// [start, end) のレコードをタイムスタンプ順で返す。
// 空の結果は該当なしを表す。保存先の読み取りエラーは呼び出し元へ返す。
```

## ありそうな誤りを区別するテスト

「状態がreadyで、使用回数が上限未満のときだけ許可する」要件なら、次のケースで条件の取り違えを区別できる。

| 状態 | 使用回数 | 上限 | 期待結果 |
| --- | ---: | ---: | --- |
| ready | 2 | 3 | 許可 |
| ready | 3 | 3 | 拒否 |
| sent | 2 | 3 | 拒否 |

常に拒否する誤り、境界を含める誤り、状態を無視する誤りを区別する。期待値は要件から決め、本体と同じ条件式をテスト内へ複製しない。
