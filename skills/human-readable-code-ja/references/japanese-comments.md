# 日本語コメントを最初から書く

日本語の自然さ、一読での文構造の追いやすさ、読者が理解するために必要な前提の3つの観点で、コードの説明を組み立てる。既存のコメントがない箇所でも、確認した仕様、実装、テストを根拠に必要な説明を書く。参考にした文章指針と転用範囲は [sources.md](sources.md) にまとめる。

## 書く内容を先に確かめる

対象の目的、入力、結果、条件、副作用、失敗のうち、読者がこの場所で知る必要のあるものを選ぶ。公開APIの利用者と内部実装の保守担当者では必要な前提が異なる。言語の基本構文を説明するかどうかも、想定読者に合わせる。

新規コメントには、根拠を確認できる定義、前提、例、因果を追加してよい。原文がないことを理由に説明を控えない。一方、実装から動作が分かっても、その採用理由や過去の経緯まで分かるとは限らない。根拠を確認できない理由は推測で書かず、確認が必要な点は作業報告で分けて伝える。

既存コメントの修正では、数値、単位、否定、限定、条件、例外、順序、確実性を保つ。コードと食い違う場合はコメントを盲信せず、仕様やテストも調べて意図する契約を確かめる。表現だけを整えて不整合を隠さない。

## 対象と動作を具体的に書く

「処理を実施する」「適切に管理する」「整合性を担保する」だけでは何が起きるか分からない。処理の対象と動詞を示し、目的を述べる必要がある場合は具体的な結果へつなぐ。特定の語句を機械的に禁止せず、文脈上の役割があるかで判断する。

```text
// 同じSKUの数量を合算し、在庫確認で注文全体の必要数と比較する。
```

このコメントは、「マップを作成する」とだけ書く場合と比べて、合算結果を後続の在庫確認でどう使うかまで伝えている。直後の代入や関数呼び出しをそのまま日本語で読み上げるだけのコメントは書かない。

主語が文脈から一意に定まる場合は省略してよい。ただし、呼び出し元、現在の関数、DB、外部サービスの間で動作主体が切り替わる箇所では、主語を明示する。処理対象（何を）や受け渡し先（どこへ）も、省略すると複数の解釈が生じる箇所では明記する。「これ」「その値」「対象」などの指示語は、指す候補が複数ある場合に具体的な名称へ置き換える。「前回と同じ」「より小さい」などの比較では、比較する対象と比較の基準を明示し、「行数の少なさより処理の追いやすさ」のように比較する双方の形と階層を揃える。

助詞の「で」や「の」によって手段、場所、動作主体、処理対象のいずれを指すか曖昧になる場合は、仕様と実装で確認した関係を具体的な動詞や助詞で書き分ける。例えば「利用者の確認」は、システムが利用者を確認するのか、利用者が内容を確認するのかを確かめて書き分ける。意味が明瞭な助詞や定着した専門用語まで、不必要に長い表現へ言い換えない。

## 条件と結果を読み違えさせない

原則として、条件節の直後にその結果を書く。一文の中に条件、逆接、例外、別主体の操作、または役割の異なる複数の列挙（「保つ前提」と「行う処理」など）を詰め込まず、意味の切れ目で文を分ける。常時行う処理と条件付きの処理を「Aと、条件のときはB」と一つの並列表現に束ねず、条件付きの処理は次の文に分ける。ただし文字数だけで機械的に区切るのではなく、長い修飾語句や括弧内の補足説明を別の文へ切り出す。短い属性や数量を表す語は、修飾する対象の近くに置く。条件節の終わりや修飾語句の境界には読点を打ち、読点だけでは係り受けが曖昧な場合は語順を変える。実装上の事実、呼び出し元が守るべき要件、未確認の推測を同じ文に混ぜない。

文を分けるときは、元の文にあった条件、否定、例外、可能性がどの操作まで掛かっていたかを確認し、分割後も同じ範囲を保つ。二文目が無条件の処理に見えてしまう場合は、条件や対象を再度明示する。また、文を並べた順序がそのまま実行順序を表すとは限らないため、処理順を記述するときは実装と一致しているか確認する。

```text
// キャッシュに値がある場合は、その値を返す。
// 値がない場合だけDBを検索する。DBの読み取りエラーは呼び出し元へ返す。
```

この例は、そのキャッシュ方針とエラー伝播が確認できた実装で使う。「値がない」と「読み取りに失敗した」を短さのためにまとめない。「必ず」「のみ」「最大」「以上」「未満」の範囲を実装と照合する。

## 列挙と論理条件を区別する

同じ役割の項目は品詞、助詞、述語の形を揃え（「単位、境界を含むか、検証済みか」ではなく「単位、境界の開閉、検証済みかどうか」）、各項目へ掛かる条件や修飾の範囲を明確にする。「公開契約と無関係な変更」のように、並列の「と」の直後に「〜と無関係な」「〜と同じ」など助詞「と」をとる修飾語が来て係り受けが衝突する表現を避け、語順や読点・補足語で境界を示す。入力、手順、結果のように役割が異なるものは、その違いが読める形で並べる。

「AやB」「A・B」だけで条件を表さない。中黒（・）は「入出力」のような対になる短い語にとどめ、3つ以上の項目や長い語句には読点や「と」「および」「または」を使う。両方が必要なのか、少なくとも一方でよいのか、片方だけなのか、例示なのかを、仕様と実装で確かめて書く。論理積（`&&`）、論理和（`||`）、排他的論理和の違いがコメントからも読み取れるようにする。次の3つはそれぞれ異なる契約を表す模式例であり、互いに言い換えられる表現ではない。

```text
// AとBが両方とも有効な場合に実行する。
// AとBの少なくとも一方が有効な場合に実行する。
// AとBのうち一方だけが有効な場合に実行する。
```

冒頭の要約マップでも、処理順、公開項目の一覧、選択肢を区別する。見た目を揃えるために、単なる一覧へ実行順を表す矢印を付けない。

## 保証の範囲を保つ

事前検証だけで「全件の書き込みが原子的」と説明したり、再試行キーがあるだけで「重複を完全に防ぐ」と断定したりしない。観測できた一例と一般的な保証を区別する。

文を短くするために、「復旧は難しい」を「復旧できない」に、「失敗する可能性がある」を「失敗する」に変えない。「効率化」「安全性の向上」のような抽象的な表現は、どの処理や性質を指すか具体的に説明する。測定していない速度や削減率は補わない。

## コードの用語と日本語を対応させる

同じ概念を「利用者」「顧客」「申請者」のように言い換えて文章に変化を付けない。異なる役割なら、それぞれの意味を区別する。同音異義の専門語（処理や責務を任せる「委譲」と、権利や所有権を移す「移譲」など）を取り違えない。コード上の識別子、API名、エラー名、パスは正確に保つ。英語名と日本語の対応が自明でなければ、初出で「予約要求（reservation request）」のように結ぶ。

専門用語は読者が知っている範囲で使う。未知の語を別の未知語へ置き換えるだけにせず、必要な箇所で意味と用途を短く説明する。日本語化のために公開名や識別子を勝手に改名しない。

プロジェクト固有の略語や長い複合名詞は、初出時に中心となる対象とその機能・構造を分けて説明する。正式名称やコード上の識別子はそのまま保ち、コメント内で略称を使う場合は最初に正式名称との対応を示す。「〜的」「〜性」「〜化」などの接尾辞は、語形だけで機械的に禁止せず、具体的な意味が伝わるかどうかで判断する。

## コメントに合う文体にする

既存の常体・敬体と句読点の規約を合わせる。規約がなければ「〜する」を基本にする。短いラベルや表のセルは体言止めでもよい。体言止めの連続で動作や条件が曖昧になるなら文にする。

「以下では処理を説明する」のような予告、「重要な役割を果たす」のような評価、依頼への返答や「LLM向けに分かりやすくした」という制作方針をコメントへ持ち込まない。ファイルの要約マップには、そのファイルの実際の役割を書く。

接続語は文順だけでは伝わらない関係に使う。「また」「さらに」「つまり」で同じ説明を繰り返さない。対比が必要な場合は対比し、項目数や語尾の変化を整えるために内容を水増ししない。「〜することができる」「〜を行う」は、意味が変わらないなら「〜できる」や具体的な動詞へ直す。

名詞や語尾の反復を機械的に消さない。短いコードコメントでは、用語と表現が揃っている方が読み取りやすい場合が多い。自然に見せるための口語、感情、比喩、意図的な崩しは不要。

## 全体像と局所の説明を分ける

冒頭の要約マップは、ファイルの役割と読む場所を示す。関数や段階の前では、その部分の目的、成立する条件、次へ渡すものを説明する。入口の契約と同じ長文を各所へ複製しない。

図は日本語ラベルと実際の識別子を組み合わせ、罫線には単純なASCIIを使ってよい。全角文字の幅に依存する複雑な整列を避け、表示環境によって崩れるなら短い箇条書きや縦方向の図へ変える。流れ、対応、状態遷移のどれかを明示し、ラベルと文で関係が読めるようにする。

## 仕上げの照合

- 各主張に仕様、実装、または確認済み資料の根拠があり、未確認の理由、性能、保証を足していないか。
- 数値、否定、限定、条件、順序、確実性、用語（同音異義語の使い分けを含む）がコードと一致しているか。
- 文を分けても条件や例外の範囲が保たれ、両方・少なくとも一方・一方だけ・例示の違いを読み取れるか。
- 並列する項目の品詞・構文や比較表現の双方の形が揃い、「Aと無関係なB」のような助詞「と」の衝突がないか。
- 一読で主体、修飾先、条件と結果が定まり、必要な前提を読者が得られるか。
- 冒頭だけでファイルの責務と読む先を把握でき、局所コメントでは次の処理の前提を理解できるか。
- 音読相当で文がねじれず、内容のない予告、評価、言い直しが残っていないか。

「AIらしいか」や推定理解率では判定しない。どの曖昧さや追跡の手間を減らしたかで評価する。
